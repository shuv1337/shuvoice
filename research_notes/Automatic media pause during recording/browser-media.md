# Browser media pause/resume on Linux Hyprland/Wayland

Research date: **October 11, 2026 PDT**. Research-only source inspection; no browser playback, GUI, installation, or configuration changes. Sources below were fetched during this research unless explicitly identified as search-result evidence. Moving `main`/`master` URLs establish current upstream implementation, not the precise code in a user's installed stable package.

## 1. Which browsers expose native MPRIS, and under what conditions?

### Takeaway
Native session-bus MPRIS is the best default integration for Chrome/Chromium and Firefox on Linux; Brave and Edge packaging also explicitly anticipates native MPRIS. Detect actual services and capabilities rather than requiring an extension or assuming a browser-name-to-service-name mapping.

### Cited Findings
- Chromium's Linux implementation exports `/org/mpris/MediaPlayer2`, `org.mpris.MediaPlayer2.Player`, explicit `Pause` and `Play`, `PlaybackStatus`, `CanPause`, `CanPlay`, and metadata on the **session D-Bus**. Upstream uses `org.mpris.MediaPlayer2.chromium.instance<PID>` and advertises `HasTrackList=false`. It reports method dispatch completion separately from subsequent playback-property updates; the implementation sends a method response after notifying observers. [Chromium Linux implementation](https://github.com/chromium/chromium/blob/main/components/system_media_controls/linux/system_media_controls_linux.cc)
- Chromium's `kHardwareMediaKeyHandling` feature is enabled by default on Linux **when built with `USE_MPRIS`**, and disabled by default without that build flag. Thus custom builds and disabled media-key integration deserve explicit diagnostics; old instructions involving `chrome://flags/#hardware-media-key-handling` should not be treated as a permanent UI contract. The current source proves the underlying feature, not availability of that flags-page entry in every release. [Current feature definition](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc)
- Firefox's GTK implementation directly owns an MPRIS session-bus name, exports the same player object/interface, maps `Pause`/`Play`/`PlayPause` to browser media actions, and reports state/capability changes. It advertises no track list. Its service suffix derives from a unique D-Bus connection name, rather than exposing a distinct player per tab. [Firefox MPRIS implementation](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp)
- Firefox's `media.hardwaremediakeys.enabled` defaults to `true`; setting it false prevents the media-key event source from opening and stops monitoring on preference change. Current defaults also include a three-second eligible-media-duration threshold and a 24-hour paused-media stop-control timer. Do not assume every sound or short clip becomes a controllable MPRIS session. [Preference defaults](https://github.com/mozilla-firefox/firefox/blob/main/modules/libpref/init/StaticPrefList.yaml); [event-source preference gate](https://github.com/mozilla-firefox/firefox/blob/main/dom/media/mediacontrol/MediaControlKeyManager.cpp)
- The Flathub Brave manifest grants `--own-name=org.mpris.MediaPlayer2.brave.*`; Edge grants `--own-name=org.mpris.MediaPlayer2.edge.*`. These are direct packaging evidence for expected branded MPRIS services, not proof that an arbitrary running release successfully exports them. [Brave manifest](https://github.com/flathub/com.brave.Browser/blob/master/com.brave.Browser.yaml); [Edge manifest](https://github.com/flathub/com.microsoft.Edge/blob/master/com.microsoft.Edge.yaml)
- Firefox's own Flatpak packaging documentation lists ownership permission for `org.mpris.MediaPlayer2.firefox.*` (search-result evidence). Its current MPRIS implementation explicitly handles Flatpak artwork paths using `XDG_DATA_HOME`. Flatpak is therefore **not intrinsically incompatible with native MPRIS**. [Firefox packaging](https://firefox-source-docs.mozilla.org/build/buildsystem/flatpak.html); [Flatpak artwork handling](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp)

### Inferences
- **Recommended product behavior:** enumerate actual MPRIS services, read capabilities and current state, and pause only observed `Playing` players that can pause. Use explicit `Pause` and later explicit `Play`, not toggle. Verify asynchronous state changes; a successful method reply alone is insufficient. This follows directly from Chromium's observer dispatch and property reporting. [Implementation basis](https://github.com/chromium/chromium/blob/main/components/system_media_controls/linux/system_media_controls_linux.cc)
- This route does not inherently need X11 key injection, a foreground window, GNOME, or Plasma: both implementations use the session D-Bus. It is a suitable Wayland/Hyprland architecture provided ShuVoice and the browser can access the appropriate session bus. [Chromium](https://github.com/chromium/chromium/blob/main/components/system_media_controls/linux/system_media_controls_linux.cc); [Firefox](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp)
- Treat Chrome/Chromium support as high-confidence upstream capability; treat Brave/Edge as expected support with runtime capability detection. Avoid hardcoding `chromium` for every derivative, given the branded Flatpak permissions. [Brave](https://github.com/flathub/com.brave.Browser/blob/master/com.brave.Browser.yaml); [Edge](https://github.com/flathub/com.microsoft.Edge/blob/master/com.microsoft.Edge.yaml)

### Gaps
- No live test of the user's installed Chrome, Chromium, Brave, Edge, Firefox, or YouTube variants was permitted. Exact distro patches, flags, extensions, private-window behavior, enterprise policy, and Flatpak overrides remain installation-specific.
- No current vendor guarantee covering every Edge/Brave release was found. Flathub manifests plus Chromium implementation are stronger than anecdote, but not equivalent to release-by-release validation.
- The current Chromium feature definition was verified; the entire current initialization path governing MPRIS under every feature combination was not traced. Do not promise a single universal troubleshooting flag.

## 2. Can native MPRIS discover all playing tabs and safely resume the original video?

### Takeaway
**No: browser-native MPRIS is an aggregated, retargetable control surface, not an inventory of every tab or media element.** It usually handles the common single-playing-YouTube case well, but a browser's active media session can change while recording, making unconditional resume unsafe.

### Cited Findings
- Chromium's system-media-controls documentation explicitly says normal SMC is a **singleton shared by all Chrome tabs and windows**. Instanced desktop-PWA controls are documented as enabled on macOS and Windows since M130. The Linux notifier explicitly calls `CreateActiveMediaController` when instanced controls are unsupported, and comments identify Linux in that case. Therefore Windows/macOS PWA behavior must not be generalized to Linux. [Architecture](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/README.md); [Linux active-controller path](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/system_media_controls_notifier.cc)
- Chromium internally has one media session per WebContents/tab. Its controller follows the active session automatically; the active session is the topmost controllable session. Audio-focus grouping allows browser tabs in the same group to play concurrently. **Internal per-tab sessions do not imply public per-tab MPRIS players.** [Controlling Media Playback](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/media_session/controlling_media_playback.md); [public internal C++ MediaSession contract](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/public/browser/media_session.h)
- Chromium's audio-focus service is a browser-process **Mojo** service. Documentation discusses gain, transient gain, and ducking; this is not a public Linux session-bus API that an unrelated recorder automatically joins. Same-group browser sessions can coexist. [Audio focus and Mojo API](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/media_session/controlling_media_playback.md)
- Firefox's service explicitly maintains multiple controllers but only one main controller for media-control keys. A controller becoming `Playing` can replace the main controller; an existing Picture-in-Picture/fullscreen controller outranks a normal controller. Thus neither the visible tab nor simply the most recently selected tab is a reliable cross-browser target rule. [Firefox selection and priority code](https://github.com/mozilla-firefox/firefox/blob/main/dom/media/mediacontrol/MediaControlService.cpp)
- Firefox's MPRIS metadata always supplies the constant `DBUS_MPRIS_TRACK_PATH` as `mpris:trackid`; KDE's MPRIS bridge similarly uses `/org/kde/plasma/browser_integration/1337`. These track IDs alone cannot establish that the same YouTube video remains selected. Chromium supplies a generated current-track path but does not expose a public tab inventory in the MPRIS player object. [Firefox metadata](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp); [KDE metadata](https://github.com/KDE/plasma-browser-integration/blob/master/host/mprisplugin.cpp); [Chromium metadata](https://github.com/chromium/chromium/blob/main/components/system_media_controls/linux/system_media_controls_linux.cc)

### Inferences
- **Resume ledger recommendation:** remember the exact service/unique owner, observed initial `Playing` state, observed pause transition, available metadata fingerprint, and subsequent state/metadata changes. Resume only entries actually paused by this recording and still confidently representing that media. A changed owner, navigation, metadata replacement, external playback, disappearance, or ambiguity should invalidate automatic resume. This is a conservative policy derived from retargetable controllers and nonunique track IDs, not a browser-provided transaction mechanism. [Chromium controller](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/system_media_controls_notifier.cc); [Firefox metadata](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp)
- Metadata heuristics still cannot prove identity perfectly: two media items can share a title, and Firefox's track ID is constant. Native MPRIS therefore cannot guarantee resuming the original tab under all interactions. Prefer skipping uncertain resume over starting an unrelated tab. [Firefox implementation](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp)
- Enumerating all MPRIS bus names can cover multiple exposed applications/browser instances, but **must not be described as pausing all playing browser tabs**. Repeatedly pausing whatever becomes active is not a reliable inventory algorithm and loses exact resume ownership. [Singleton design](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/README.md)
- Merely opening ShuVoice's microphone should not be assumed to claim browser audio focus or auto-pause YouTube: the cited browser focus service is internal, not a general Linux microphone arbitration contract. [Focus documentation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/media_session/controlling_media_playback.md)

### Gaps
- Exact behavior for multiple media elements in one tab, ads replacing YouTube's content element, live streams, embeds, and custom Media Session action handlers requires a browser/site test matrix. Current source proves aggregation and routing, not uniform YouTube behavior.
- Purely observing pause and metadata signals cannot always distinguish user intent from the recorder's own pause, especially if the user intentionally leaves an already-paused video paused. No atomic pause-with-ownership/resume-original-tab contract was identified in native browser MPRIS.

## 3. Which fallbacks are worthwhile?

### Takeaway
Use an optional extension/native host for stronger per-tab/element identity if needed; keep CDP an opt-in development/advanced route. Multimedia keys do not solve target identity, while PipeWire mute/duck is a distinct sound-suppression feature, not real video pause.

### Cited Findings
- Plasma Browser Integration has two required parts: a browser extension and native host. KDE documents media controls for websites and lists Chrome/Chromium/Vivaldi, Firefox, and Edge extension distribution. The host directly registers an MPRIS service named `org.mpris.MediaPlayer2.plasma-browser-integration` with an instance suffix, and maintains a single player object. Installing it does not itself establish one discoverable MPRIS player per tab. [KDE documentation](https://community.kde.org/Plasma/Browser_Integration); [native MPRIS source](https://github.com/KDE/plasma-browser-integration/blob/master/host/mprisplugin.cpp)
- Chrome native messaging requires a registered native host manifest and extension integration; Linux manifest locations vary by browser, and the host path is absolute. This creates real packaging and browser-profile work beyond native MPRIS. [Chrome native-messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)
- Firefox's current confined-native-messaging documentation says Flatpak/Snap cannot ordinarily locate/launch arbitrary host native-messaging programs. It documents both the WebExtensions portal and newer Native Messaging Proxy, associated preferences, and explicitly says availability is not universal; the proxy is described as available in Ubuntu 26.04. Thus both “Flatpak native messaging never works” and “installing the extension is sufficient” are outdated/overbroad. [Current Firefox confinement documentation](https://firefox-source-docs.mozilla.org/toolkit/components/extensions/webextensions/native-messaging-portal-design.html)
- CDP provides `Target.getTargets` and `Runtime.evaluate`, enabling target-specific inspection and JavaScript execution when a debugging connection is deliberately available. Chrome 136 changed remote-debugging-port/pipe switches so they are not respected against the default Chrome data directory; a nonstandard `--user-data-dir` is required for that switch-based route. [CDP Target](https://chromedevtools.github.io/devtools-protocol/tot/Target/); [CDP Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/); [Chrome remote-debugging change](https://developer.chrome.com/blog/remote-debugging-port)
- Firefox's current remote-protocol README lists WebDriver classic and WebDriver BiDi. Do not presume a Chrome CDP adapter is the shared current Firefox automation backend. [Firefox remote README](https://github.com/mozilla-firefox/firefox/blob/main/remote/README.md)
- Multimedia play/pause actions operate on the browser's selected active controller; Firefox explicitly only permits one main controller, and Chromium documents the active-session media-key route. They provide no extra tab inventory or pause ownership. [Chromium key routing](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/media_session/controlling_media_playback.md); [Firefox routing](https://github.com/mozilla-firefox/firefox/blob/main/dom/media/mediacontrol/MediaControlService.cpp)
- `wpctl set-volume` changes a PipeWire node's volume, and `wpctl set-mute` changes its mute state; `--pid` can affect all matching process nodes. The documented operations concern audio graph nodes rather than browser media playback timelines. [WirePlumber wpctl manual](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html)

### Inferences
- **Preferred fallback order:** native MPRIS → optional purpose-built extension/native host for explicit YouTube/tab identity → explicitly configured automation backend when appropriate. An extension can maintain a ledger of tab/frame/element identities and paused elements, but access permissions, document navigation, cross-origin frames, dynamic elements, and play failures must still be handled. This is a proposed design, not a claim that every extension or all tabs are automatically accessible. [Native messaging foundation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging); [CDP target/runtime alternatives](https://chromedevtools.github.io/devtools-protocol/tot/Target/)
- Plasma integration is an existing bridge worth recognizing when installed, not a required Hyprland dependency. Its direct session-bus MPRIS host suggests media control can be usable outside Plasma, but full Hyprland compatibility was not tested. Native browser MPRIS plus the extension may expose duplicate representations of the same media; deduplication or selecting one integration is prudent. [KDE host implementation](https://github.com/KDE/plasma-browser-integration/blob/master/host/mprisplugin.cpp)
- Synthetic multimedia keys should be last-resort/manual behavior: they inherit active-player ambiguity and toggles can accidentally start media. Sending keys also adds compositor binding/focus assumptions that direct session-bus calls avoid. [Active-controller semantics](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/media_session/controlling_media_playback.md)
- PipeWire duck/mute can suppress sound from otherwise uncontrollable sources, but it does not issue HTML media `pause` or MPRIS `Pause`; the video may continue advancing and content may be missed. Expose this as “mute/duck while recording,” separately from “pause and resume.” Restore only owned changes, preserve prior volume/mute, and do not mute the microphone being recorded. [wpctl operation semantics](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html)

### Gaps
- Plasma extension's detailed current tab-selection algorithm and current Flatpak integrator behavior were not fully traced. The inspected host proves a single player surface, not extension-side all-tab control or a validated Hyprland deployment.
- No guarantee was established that an extension can capture every media source (Web Audio, inaccessible frames, protected pages, or arbitrary site players). “All playing browser tabs individually discoverable” is specifically unsupported.
- CDP startup and attachment policies in every current Brave/Edge build were not verified; Chrome's default-directory restriction should not be asserted as an identical vendor policy without testing.
- WirePlumber automatic role-based ducking configuration was not verified for the user's version. The verified fallback is explicit node volume/mute control; no claim is made that microphone capture automatically ducks browser audio or that every browser tab maps to a separate PipeWire node.
