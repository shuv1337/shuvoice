# Linux media control for ShuVoice automatic recording pause

Research reference date: **2026-10-11 PDT**. Primary specifications, upstream source, crate documentation, and Spotify API documentation were fetched live for this assignment. These are research findings, not results of playback testing; no playback commands or installs were performed. Rolling `main`/`master` sources describe the fetched source, not a guaranteed installed release.

## What MPRIS contract makes pause/resume correct?

### Takeaway
Use the user's session D-Bus and explicit MPRIS `Pause`/`Play`, retaining an utterance-scoped record of exactly which running player instances were playing and were successfully observed paused. Resume conservatively against the original unique D-Bus owner, never by a freshly selected default player; MPRIS cannot provide perfect attribution of user intent or atomic conditional resume.

### Cited Findings
- MPRIS 2.2 defines discovery through names beginning `org.mpris.MediaPlayer2`, instance-specific suffixes, and the fixed `/org/mpris/MediaPlayer2` object implementing the root and `.Player` interfaces. Instance suffix format is an example, not a dependable PID parser. — [MPRIS naming/entry point](https://specifications.freedesktop.org/mpris-spec/latest/)
- D-Bus `ListNames` lists currently owned names; `GetNameOwner` resolves a well-known name to its unique connection name. A unique name is never reassigned during that bus's lifetime; `NameOwnerChanged(name, old_owner, new_owner)` reports appearance, disappearance, or replacement. This is stronger identity than an application label or PID. — [D-Bus names](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus-names), [ownership signal](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-name-owner-changed), [GetNameOwner](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-get-name-owner)
- `PlaybackStatus` is `Playing`, `Paused`, or `Stopped`; changes emit `PropertiesChanged`. `Pause` on an already paused player has no effect; subsequent `Play` resumes from the same position. `PlayPause` toggles (and can start stopped media); `Stop` changes the expected subsequent start position to the beginning. Thus toggles and stop are the wrong primitives. — [Player methods/properties](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html)
- Gate pause on `CanControl && CanPause`; gate restoration on `CanControl && CanPlay`. `CanPause` and `CanPlay` are capabilities, **not playback-state booleans**. `CanControl=false` means no control methods are implemented. `CanControl` is not expected to change and does not emit change signals; the other relevant properties do. Some disabled methods are specified to do nothing, so a successful method reply is insufficient proof of a state change. — [Capabilities and method semantics](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html#Property:CanControl)
- Metadata must include `mpris:trackid` for a current track; `PropertiesChanged` covers metadata changes. `Position` specifically does not emit that signal, while `Seeked` reports discontinuities. Only `SetPosition`, not `Play` or `Pause`, accepts a track ID to protect against stale operations. — [Metadata, Position, SetPosition](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html)
- D-Bus supports `NO_AUTO_START`; property change signals can contain invalidated names as well as changed values. MPRIS has no pause lease, origin-of-state-change field, compare-and-swap playback command, or user-interaction revision counter in the Player interface. — [D-Bus message flags/properties](https://dbus.freedesktop.org/doc/dbus-specification.html), [complete Player interface](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html)

### Inferences
- Recommended transaction (engineering policy, not an MPRIS guarantee): subscribe to ownership/property changes before discovery/snapshot, resolve every matching live name to its unique owner, deduplicate aliases by `(owner, object path)`, obtain a fresh state/capability/track snapshot, and pause only `Playing` eligible endpoints. Address calls directly to the resolved unique owner, and never start activatable players. Match signal sender + object path + interface, rather than accepting arbitrary matching signal names. Basis: [D-Bus ownership/routing](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus), [MPRIS contract](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html).
- Record a lease only after a successful pause exchange plus bounded fresh-state/signal confirmation of `Paused`; preserve the baseline owner and track identity from before pause. At recording end, freshly read state/capabilities, require the same owner still holds the original name and the same media identity where reliable, and issue explicit `Play` only for the surviving eligible lease. Never run “play all paused players.” A restart, bus reconnect, changed track, `Stopped`, or observed user-driven play/seek should invalidate restoration. If media became `Playing` independently, drop the lease and do not repeatedly fight it. Basis: [state/track semantics](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html), [unique names](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus-names).
- Subscribe-first plus snapshot/reconciliation reduces missed-event windows but is not a distributed transaction: signals and snapshots can race, and track comparison immediately before `Play` cannot make that method conditional. A manual `Pause` while already paused may produce no observable change; ShuVoice cannot promise “never resume after user pause.” Document conservative best effort and provide a way to suppress restoration. Basis: [idempotent Pause and argument-free Play](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html).
- A timed-out pause is an **unknown outcome**, not proof it was not delivered. Do not blindly retry or grant normal restoration ownership; bounded readback can aid diagnostics, but cannot establish causality. Account for a pause completing after recording has already ended: use recording-generation IDs and an explicit pending/finishing state so late completions cannot attach to a later utterance. Basis: [method calls/replies](https://dbus.freedesktop.org/doc/dbus-specification.html#message-protocol-types), [zbus timeout semantics](https://docs.rs/zbus/5.19.0/zbus/connection/struct.Builder.html#method.method_timeout).
- Keep this off the audio callback and session actor's blocking path. Suggested initial budgets (to benchmark, not sourced performance numbers): parallel bounded per-player RPCs around 150–300 ms and a total pre-record pause budget around 300–500 ms; recording proceeds when media control is unavailable. Release after microphone capture actually stops, including cancellation/start failure/shutdown, rather than after ASR/network/transcript injection. Serialize very short consecutive utterances to prevent stale restore from overlapping new recording. These are product recommendations derived from asynchronous RPC behavior, not measured latency guarantees. — [D-Bus asynchronous design](https://dbus.freedesktop.org/doc/dbus-specification.html#introduction)

### Gaps
- No live Spotify/YouTube timing, account-tier, or user-race experiment was permitted. Exact budgets need measurement. No protocol can guarantee recovery after ShuVoice is killed before cleanup without a separately designed recovery agent; blindly persisting leases across restart would risk unwanted playback.
- Strict restoration when a browser supplies missing, constant, or session-level track identifiers remains a product tradeoff: skip uncertain resume (safer) versus owner-only best effort (more convenient). Track identity is not necessarily tab identity.

## Which implementation should ShuVoice use: playerctl, Rust mpris, or zbus?

### Takeaway
Prefer a small native async **zbus MPRIS client**, with pure lease policy separate from D-Bus I/O. `playerctl` is valuable for diagnostics/prototypes; the synchronous `mpris` crate is viable on a dedicated thread but offers a poorer fit for fine-grained async lifecycle coordination.

### Cited Findings
- `playerctl` is both a CLI and a GLib/GObject-introspectable library. It supports discovery (`--list-all`), status, explicit pause/play, selection lists, `--all-players`, and query `--follow`; without selection it acts on the first player found. `--player=vlc,spotify` picks the first matching instance supporting the command; `%any` is a priority wildcard. — [Upstream README](https://github.com/altdesktop/playerctl#selecting-players-to-control)
- `playerctld` monitors activity and makes selection follow the last-active ordering. `--follow` can switch the player it reports as players appear/disappear or priority changes, and prints a newline when no player supports the query. Neither the default-selection contract nor last-active ordering preserves the identity of the player paused earlier. — [playerctld and following](https://github.com/altdesktop/playerctl#following-changes)
- Rust `mpris` **2.1.0** (docs dated September 23, 2026) uses `dbus ^0.9.6`, exposes `unique_name`, identity, bus name, capabilities, explicit methods, and configurable `set_dbus_timeout_ms`. `Player` is `!Send` and `!Sync`; `events()` returns a blocking iterator. `checked_pause`/`checked_play` return whether a command was sent, not that playback state was verified. — [Versioned Player documentation](https://docs.rs/mpris/2.1.0/mpris/struct.Player.html)
- The same crate deprecated guessing the “player name part” because MPRIS does not standardize the instance suffix syntax. Keep complete bus names for instance matching. — [Deprecation rationale](https://docs.rs/mpris/2.1.0/mpris/struct.Player.html#method.bus_name_player_name_part)
- zbus **5.19.0** offers async proxy building with explicit destination/path/interface, configurable property caching or uncached properties, session connections, and connection-level `method_timeout(Duration)` returning a timeout I/O error. Runtime dependencies include optional Tokio support. — [Proxy builder](https://docs.rs/zbus/5.19.0/zbus/proxy/struct.Builder.html), [Connection builder](https://docs.rs/zbus/5.19.0/zbus/connection/struct.Builder.html)

### Inferences
- zbus permits the precise owner-addressed queries, subscriptions, fresh readbacks, and cancellation-aware orchestration required above without CLI output parsing or per-operation subprocesses. Define only the MPRIS client surface needed; a crate advertised as an MPRIS **server** is not the needed abstraction. Avoid trusting cached `PlaybackStatus` as the final restore predicate; explicit uncached `Properties.Get/GetAll` should supplement event tracking. — [zbus destination/cache controls](https://docs.rs/zbus/5.19.0/zbus/proxy/struct.Builder.html)
- Use `playerctl --list-all` and explicit per-instance status as read-only troubleshooting examples. A shell sequence “pause default; record; play default” is incorrect because default selection can change; “pause all; play all” also starts media that was already paused. Calling the full CLI instance name reduces selection ambiguity but does not by itself preserve unique-owner continuity across restart. — [selection behavior](https://github.com/altdesktop/playerctl#selecting-players-to-control), [D-Bus ownership](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus-names)
- Exclude synthetic aggregators such as the playerctld MPRIS endpoint from native enumeration, rather than controlling the aggregator and underlying real players twice. Do not use playerctld's most-recently-active choice as a restore handle: even a stable proxy owner need not imply a stable underlying target. This is an architectural consequence of its documented dynamic selection, not a newly reproduced bug. — [playerctld purpose](https://github.com/altdesktop/playerctl#about)
- If choosing `mpris`, construct and retain its `!Send` objects inside a dedicated worker thread and bridge bounded commands/events to ShuVoice; simply wrapping an already constructed Player in a multithreaded async task is unsuitable. Native zbus still requires testing malformed/invalidated properties, vanished owners, RPC stalls, reordered lifecycle completions, and dropped subscriptions. — [mpris threading/events](https://docs.rs/mpris/2.1.0/mpris/struct.Player.html)

### Gaps
- Repository dependency/MSRV compatibility was not audited; the versioned docs establish capabilities, not a recommendation to upgrade ShuVoice indiscriminately. The attempted upstream `playerctl/playerctld.c` URL returned 404, so no source-level claim about its exact forwarding internals or timeout defaults is made.

## How well does this cover Spotify, Flatpak, and YouTube browsers; is Spotify Web API better?

### Takeaway
MPRIS is the practical local, compositor-independent first choice for Spotify and browser-exported YouTube sessions. Flatpak Spotify explicitly permits its MPRIS name; browser media-session aggregation and imperfect application implementations limit precision. Spotify Web API adds account/device/network restrictions and is a poor default for local microphone recording.

### Cited Findings
- Upstream playerctl explicitly lists Spotify and web browsers among supported MPRIS players. Its troubleshooting notes that Spotify discovery can fail when applications lack the correct D-Bus session environment. This is an environment prerequisite, not evidence that Hyprland needs media-key injection. — [playerctl supported players and troubleshooting](https://github.com/altdesktop/playerctl)
- Current Flathub Spotify manifest uses app ID `com.spotify.Client`, permits `--own-name=org.mpris.MediaPlayer2.spotify`, and exports `com.spotify.Client.desktop`; it also supports Wayland and fallback X11. Thus sandboxing does not inherently hide Spotify's MPRIS service from a host-session client. — [Flathub maintained manifest](https://raw.githubusercontent.com/flathub/com.spotify.Client/master/com.spotify.Client.json)
- An upstream playerctl-maintained Spotify support letter requests better track metadata, position, and volume support. This is historical compatibility evidence, **not** proof current pause/status is broken; ShuVoice should use the narrow capability-checked pause/play subset instead of assuming complete MPRIS compliance. — [Upstream support letter](https://raw.githubusercontent.com/altdesktop/playerctl/master/letter-to-spotify-support.md)
- Current Chromium Linux source registers `org.mpris.MediaPlayer2.chromium.instance<PID>` on the shared **session** bus; it exports explicit `Pause` and `Play`, `PlaybackStatus`, `CanControl`, `CanPause`, and `CanPlay`, and delegates methods to media-controls observers. Identity is the product name. Metadata includes track ID/title/artist/album/length/artwork when available; this implementation does not emit `xesam:url` in its metadata builder. — [Chromium Linux implementation](https://raw.githubusercontent.com/chromium/chromium/main/components/system_media_controls/linux/system_media_controls_linux.cc)
- Chromium's exported identity is process-scoped and its Player interface has no tab ID parameter. The cited source proves a Linux MPRIS route, not that every audible tab is separately discoverable or that a bus name identifies YouTube specifically. — [service name and method handlers](https://raw.githubusercontent.com/chromium/chromium/main/components/system_media_controls/linux/system_media_controls_linux.cc)
- Spotify Web API pause requires OAuth 2.0 scope `user-modify-playback-state` and **Spotify Premium**. If `device_id` is omitted it targets the user's currently active device; ordering with other Player API endpoints is not guaranteed. Documented responses include 204, 401, 403, and 429. — [Pause Playback API](https://developer.spotify.com/documentation/web-api/reference/pause-a-users-playback)
- Current Spotify quota documentation says development apps require a Premium app owner, permit up to **5 authenticated allowlisted users**, and enforce account-level quota buckets in addition to rate limits. Non-allowlisted token requests can receive 403. Extended-access applications have accepted organizations only since May 15, 2025; listed entry requirements include an established business, launched service, and at least **250k MAUs**. Do not repeat the obsolete 25-user development limit. — [Current quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)

### Inferences
- Native and Flatpak Spotify should use the same discovered MPRIS interface, not separate API adapters or hardcoded desktop-file identifiers. Keep full well-known name + unique owner; neither `Identity=Spotify` nor `DesktopEntry` alone identifies an instance. The manifest also means simultaneous native and Flatpak clients can contend for the same well-known name; do not assume both are independently exposed. — [Flathub bus permission](https://raw.githubusercontent.com/flathub/com.spotify.Client/master/com.spotify.Client.json), [D-Bus name ownership](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus-names)
- Hyprland/Wayland is not an impediment to session D-Bus control: there is no need to focus Spotify/browser windows or synthesize global media keys. The ShuVoice user service must connect to the same user/session bus as those applications. Avoid copying old README `dbus-launch`/X11 recipes into modern systemd/Hyprland setup without diagnosing the actual bus mismatch. — [Chromium shared-session bus](https://raw.githubusercontent.com/chromium/chromium/main/components/system_media_controls/linux/system_media_controls_linux.cc), [playerctl environment caveat](https://github.com/altdesktop/playerctl#no-players-found)
- Scope the promise to **playing MPRIS sessions**, not “all audible applications/tabs.” If several real endpoints are Playing, pausing each eligible endpoint is appropriate for preventing microphone contamination; selecting only Spotify because it ranks first leaves browser audio running. Browser content may switch within one owner during recording; fresh metadata/state checks reduce but cannot eliminate wrong-tab resume. YouTube-only filtering cannot rely on Chromium MPRIS URL metadata that the cited implementation does not provide. — [Chromium metadata/methods](https://raw.githubusercontent.com/chromium/chromium/main/components/system_media_controls/linux/system_media_controls_linux.cc)
- Do not impose Web API Premium/OAuth constraints on local MPRIS: MPRIS itself specifies neither, although actual Spotify account/ad behavior still needs testing. Web API is an opt-in remote-device alternative only; always bind the device and refresh state rather than blindly controlling the account's active device, and do not transfer playback as part of pause/resume. — [MPRIS](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html), [Web API target/restrictions](https://developer.spotify.com/documentation/web-api/reference/pause-a-users-playback)

### Gaps
- Firefox-specific source, current browser flags, multiple-tab selection behavior, private windows, ads/live streams, and sandboxed-browser permissions need separate browser-focused research/testing; Chromium source alone does not establish them.
- Spotify is proprietary; fetched primary material does not establish current signal reliability across Linux builds, Flatpak overrides, free-account ads, or Spotify Connect remote playback. MPRIS has no standardized active-output-device identity, so local Spotify's exported Playing status must not be equated with proof audio is playing on this machine. These cases should be acceptance tests and documented best-effort limits.
