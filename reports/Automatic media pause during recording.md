# Pause media safely around ShuVoice recording

*Research date: October 11, 2026 PDT. Source and specification research; no implementation or live playback testing.*

**Use native MPRIS over the session D-Bus, implemented with an asynchronous Rust `zbus` adapter, as ShuVoice’s first solution.** This offers one local control path for Spotify and browser-exposed YouTube playback without window focus, synthetic keys, browser extensions, or Spotify OAuth. Pause eligible playing sessions at an admitted recording start; resume only the original player instances that ShuVoice successfully paused and still has reason to restore. The important limitation is that browser MPRIS generally represents a selected media session, **not every playing tab**, and cannot guarantee exact resume ownership after all user interactions. Integrate this into ShuVoice’s session lifecycle: recording includes a microphone tail after key-up, while preroll can already contain media audio. Ship a narrowly described, initially opt-in feature; add a purpose-built browser extension only if actual YouTube compatibility tests establish that native control is insufficient.

## Native MPRIS covers the priorities, but not every sound

MPRIS defines discoverable `org.mpris.MediaPlayer2…` names, a fixed player object, playback status, capabilities, and explicit `Pause` and `Play`. It operates over D-Bus rather than compositor input, making it a natural fit for Hyprland/Wayland. Pause only when `PlaybackStatus=Playing` and `CanControl && CanPause`; restoration additionally requires `CanPlay`. **Never use `PlayPause` or `Stop`:** toggling can start media, while stopping changes subsequent playback-position semantics. A successful method reply does not establish that playback actually paused, because unsupported operations can be no-ops. ([MPRIS specification](https://specifications.freedesktop.org/mpris-spec/latest/), [Player interface](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html))

Spotify is explicitly supported by upstream playerctl, and Spotify’s maintained Flathub manifest permits ownership of `org.mpris.MediaPlayer2.spotify`. Native and Flatpak installations should therefore use the same discovered interface rather than separate adapters. This establishes a supported integration route, not verified behavior of this host’s installed client. Spotify’s historical MPRIS shortcomings concern broader metadata, position, and volume support; they justify testing the narrow pause/status/play subset rather than declaring current pause broken. Local MPRIS itself requires neither OAuth nor Premium. Free-account advertisements and Spotify Connect still need validation: MPRIS has no standardized active-output-device identity, so a local client’s `Playing` state does not prove sound is coming from this machine. ([playerctl](https://github.com/altdesktop/playerctl), [Spotify Flatpak manifest](https://raw.githubusercontent.com/flathub/com.spotify.Client/master/com.spotify.Client.json), [historical support letter](https://raw.githubusercontent.com/altdesktop/playerctl/master/letter-to-spotify-support.md))

Chromium and Firefox both implement native Linux MPRIS. Chromium’s media-key integration defaults on when built with `USE_MPRIS`; Firefox’s `media.hardwaremediakeys.enabled` defaults true. Brave and Edge Flatpak manifests explicitly permit branded MPRIS names, supporting capability detection rather than hardcoded Chromium naming. Flatpak is not inherently incompatible with this route. Disabled integration, custom builds, session-bus mismatch, and sandbox overrides remain installation-specific caveats; no installed browser, Spotify build, or live service name was inspected in this research. ([Chromium implementation](https://github.com/chromium/chromium/blob/main/components/system_media_controls/linux/system_media_controls_linux.cc), [Chromium feature definition](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc), [Firefox implementation](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp), [Firefox defaults](https://github.com/mozilla-firefox/firefox/blob/main/modules/libpref/init/StaticPrefList.yaml), [Brave manifest](https://github.com/flathub/com.brave.Browser/blob/master/com.brave.Browser.yaml), [Edge manifest](https://github.com/flathub/com.microsoft.Edge/blob/master/com.microsoft.Edge.yaml))

**YouTube’s common single-playing-video case is the strongest browser target, but remains untested here.** Chromium documents a singleton system-media-control surface shared across tabs/windows; Linux follows its active media controller. Firefox also selects one main controller, with Picture-in-Picture/fullscreen priorities. Multiple tabs can therefore play without becoming independently enumerable MPRIS players. Firefox supplies a constant track ID, while Chromium’s inspected metadata builder does not expose `xesam:url`; neither browser gives ShuVoice a dependable YouTube-tab inventory through MPRIS. Pause every eligible real endpoint discovered at start, but describe the feature as controlling “supported playing media sessions,” not “all tabs” or “all audible applications.” ([Chromium architecture](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/README.md), [Linux controller path](https://github.com/chromium/chromium/blob/main/content/browser/media/system_media_controls/system_media_controls_notifier.cc), [Firefox selection](https://github.com/mozilla-firefox/firefox/blob/main/dom/media/mediacontrol/MediaControlService.cpp), [Firefox metadata](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/MPRISServiceHandler.cpp))

## Alternative controls add costs without fixing ownership

**Native `zbus` is the recommended production transport.** It offers asynchronous session connections, explicit destinations, property-cache controls, and method timeouts suitable for owner-addressed operations and fresh readbacks. ShuVoice already uses Tokio; its inspected manifests contain no existing MPRIS/D-Bus client dependency. Evaluate the chosen crate version’s features and MSRV before adoption. The synchronous Rust `mpris` crate is viable on a dedicated thread, but its `Player` is neither `Send` nor `Sync`, its event iterator blocks, and “checked” commands report dispatch rather than confirmed playback state. ([zbus proxy builder](https://docs.rs/zbus/5.19.0/zbus/proxy/struct.Builder.html), [connection builder](https://docs.rs/zbus/5.19.0/zbus/connection/struct.Builder.html), [mpris 2.1.0](https://docs.rs/mpris/2.1.0/mpris/struct.Player.html), [workspace dependencies](../Cargo.toml), [IO dependencies](../crates/shuvoice-io/Cargo.toml))

**playerctl is excellent for diagnostics and prototypes**, but a shell wrapper would inherit executable dependencies and subprocess ownership work without gaining a richer protocol. Its default selects the first player; playerctld introduces last-active selection. Consequently, “pause default, then play default” can resume a different application, and “pause all, then play all” starts previously paused media. Explicit instance selection helps but does not preserve unique-owner identity across restart. Exclude dynamic aggregators such as playerctld from native enumeration to avoid controlling both proxies and underlying players. ([player selection and following](https://github.com/altdesktop/playerctl#selecting-players-to-control))

**An extension with native messaging is the best second-stage browser option** when exact tab/frame/element identity matters. It can maintain an element-specific ledger, subject to permissions, navigation, cross-origin frames, dynamic players, and playback failures. It adds extension distribution and browser-specific native-host installation. Confined Firefox native messaging has portal/proxy arrangements whose availability is not universal. Existing Plasma Browser Integration is worth recognizing, but its native host exposes a single MPRIS player, not automatically one endpoint per tab; simultaneous native and extension representations also create duplication risks. Full Hyprland compatibility was not tested. ([Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Firefox confinement](https://firefox-source-docs.mozilla.org/toolkit/components/extensions/webextensions/native-messaging-portal-design.html), [KDE integration](https://community.kde.org/Plasma/Browser_Integration), [KDE host](https://github.com/KDE/plasma-browser-integration/blob/master/host/mprisplugin.cpp))

CDP can enumerate targets and execute element-specific JavaScript, but is an advanced opt-in/debugging integration. Chrome 136 restricted switch-based remote debugging of the default data directory, requiring a nonstandard `--user-data-dir`; Firefox’s current remote stack documents WebDriver/BiDi rather than a common CDP backend. Synthetic media keys provide less targeting information than MPRIS and inherit active-controller ambiguity. PipeWire/WirePlumber mute or duck changes audio-node volume, **not the playback timeline**: the user can miss video content while recording. Keep that as a separately named sound-suppression feature. ([CDP targets](https://chromedevtools.github.io/devtools-protocol/tot/Target/), [Chrome debugging change](https://developer.chrome.com/blog/remote-debugging-port), [Firefox remote protocols](https://github.com/mozilla-firefox/firefox/blob/main/remote/README.md), [wpctl](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html))

Spotify Web API is a poor default for local recording: pause requires Premium, OAuth scope `user-modify-playback-state`, network access, and deliberate device selection; without `device_id`, it controls the account’s active device. Ordering across Player endpoints is not guaranteed. Current development-mode documentation also limits apps to five authenticated allowlisted users and requires a Premium owner. Reserve it for an explicitly requested remote-device feature, never automatic playback transfer. ([Pause Playback API](https://developer.spotify.com/documentation/web-api/reference/pause-a-users-playback), [quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes))

## Resume requires a conservative ledger, not a toggle

The proposed coordinator should subscribe before discovery, resolve well-known names to unique D-Bus owners, and deduplicate aliases by owner/object path. Unique names are not reassigned during a bus lifetime; application labels and instance-name suffixes are weaker identities. Address operations to the resolved owner without activating absent applications. Snapshot initial playback/capabilities and available media identity, then record restoration entitlement only after a successful pause exchange plus bounded confirmation of `Paused`. Property invalidations require fresh reads, and signals must match the expected sender/object/interface. ([D-Bus ownership](https://dbus.freedesktop.org/doc/dbus-specification.html#message-bus-names), [GetNameOwner](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-get-name-owner), [MPRIS properties](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html))

Before restoring, freshly check the original name’s owner, state, capabilities, and available identity fingerprint. Drop entitlement on disappearance, replacement, bus reconnection, changed media, `Stopped`, or observed conflicting playback/seek activity. If a user independently resumes playback, do not repeatedly pause it. Metadata used for identity can remain ephemeral and out of logs. Conservative fingerprint checks are still heuristics: a constant track ID or unchanged title cannot prove the original browser tab remains selected. Strictly skipping uncertain browser restoration is safer but less convenient than owner-only restoration; that tradeoff must be explicit.

**MPRIS cannot provide perfect pause ownership.** There is no lease, action-origin field, user-interaction revision, or conditional `Play(track_id)`. A user pressing Pause while already paused can produce no observable change, and a target can change between the final check and `Play`. Even a confirmed pause transition cannot prove causality against simultaneous user action. Offer a way to suppress restoration and describe it as conservative best effort, not “never overrides user intent.” A timeout is an unknown outcome: cancellation cannot retract an already delivered command, and readback cannot retroactively establish who caused a pause. ([complete Player contract](https://specifications.freedesktop.org/mpris-spec/latest/Player_Interface.html), [D-Bus calls](https://dbus.freedesktop.org/doc/dbus-specification.html#message-protocol-types))

## ShuVoice needs capture-boundary integration, not keybinding hooks

**Observed code:** `request_start_recording_with_case` admits starts, initiates ASR reset, and sets pending state; `complete_start_recording` later declares recording. Control acknowledgment is not proof recording began. `stop_recording` clears recording at key-up, but a pending chunk can delay finalization, after which late microphone input remains accepted for `STOP_TAIL_GRACE=120 ms`. CPAL capture itself runs continuously. Thus neither key-up nor “stop plus 120 ms” is a safe resume boundary, and waiting for transcript injection unnecessarily prolongs the pause. ([session lifecycle](../crates/shuvoice-app/src/session.rs#L685-L983), [tick/tail routing](../crates/shuvoice-app/src/session.rs#L1864-L1944), [finalize](../crates/shuvoice-app/src/finalize.rs#L106-L202), [audio bridge](../crates/shuvoice-cli/src/compose/audio_bridge.rs#L495-L509))

**Proposed architecture:** keep policy/config in `shuvoice-core`, a nonblocking media seam in `shuvoice-app`, the D-Bus adapter in `shuvoice-io`, and coordinator lifetime wiring in CLI/runtime composition. Allocate a recording-intent epoch at admission, distinct from ASR generation, and carry it through both reset and media completions. Acquire pauses concurrently with reset; declare Listening after reset and bounded pause acquisition settle. An initial total acquisition budget around 300–500 ms is a benchmark hypothesis, not a measured requirement. Missing or stalled media control should fail open for recording, without triggering the ASR breaker or dependency exit 78. Actor responsiveness matters: its loop ticks every 10 ms, and UI status events are coalescible, so status observation is not an ownership protocol. ([traits](../crates/shuvoice-app/src/traits.rs), [runtime actor](../crates/shuvoice-app/src/runtime.rs#L456-L507), [events](../crates/shuvoice-app/src/events.rs), [ASR generations](../crates/shuvoice-app/src/asr_owner.rs#L140-L160), [repository contracts](../AGENTS.md))

Introduce an authoritative **utterance capture-closed transition**: no more microphone samples can enter that utterance, even though physical capture continues. Release then, independently of decode/commit/injection. Reconcile per-player operations across rapid stop/start: a late successful pause remains an owned effect; transfer its entitlement to a newer hold rather than resuming into the next recording. Recheck desired state before sending Play. If Play has already been sent, the next start must settle/re-pause or report degraded protection. Cover pending cancellation, reset failure, terminal ASR failure, TTS takeover, supersession, and shutdown centrally; nonterminal recovery retains the hold. Runtime should own cleanup independently of the actor, including forced actor abort. SIGKILL recovery cannot be promised. ([cancellation precedent](../crates/shuvoice-app/src/session.rs#L985-L1029), [reset completions](../crates/shuvoice-app/src/session.rs#L1395-L1456), [shutdown](../crates/shuvoice-app/src/runtime.rs#L276-L340))

Preroll is a separate problem. The inspected default is 200 ms, and the app combines untimestamped buffered samples with retained preroll. Backend queues and partially assembled CPAL chunks can contain pre-pause audio even after an app-ring clear. For the first version, recommend preserving speech preroll and explicitly promising only best-effort contamination reduction. A strict clean boundary requires timestamp/sequence fencing across all buffers and trimming before a confirmed boundary, potentially clipping speech begun before readiness. ([preroll](../crates/shuvoice-app/src/session.rs#L1857-L1900), [default](../crates/shuvoice-core/src/config/model.rs#L204), [CPAL chunk assembly](../crates/shuvoice-io/src/audio/cpal_source.rs#L215-L274))

## Validate races first, then the actual players

Keep initial scope to opt-in recording-only MPRIS control, an admission-time snapshot of eligible endpoints, and conservative restoration. Do not chase newly appearing players or extend the hold through ShuVoice TTS without a separate product decision. Core-owned configuration needs settings/schema/docs coverage; preserve feature-off builds. Current capture-error plumbing logs CPAL errors without a typed fatal event reaching the session, so reliable device-loss release would require additional work. ([repository contracts](../AGENTS.md), [TTS handoff](../crates/shuvoice-app/src/session.rs#L2030-L2096), [capture errors](../crates/shuvoice-io/src/audio/cpal_source.rs#L220-L274))

Highest-value proposed tests use the existing fake-clock/session harness and a controllable transport: stop during pending pause/reset; stale completion after a newer start; late pause success; resume already dispatched; stop before the first recording tick; slow chunks extending the tail; partial player failures; owner replacement; unknown timeout outcomes; and bounded shutdown. Private-bus fake services should cover capabilities, invalidated properties, alias deduplication, and bus reconnection. Existing slow-reset, late-audio, non-cancellable-effect, and forced-shutdown tests are useful anchors, not results certified by this research. ([runtime harness](../crates/shuvoice-app/src/runtime.rs#L524-L617), [regression anchors](../crates/shuvoice-app/tests/ship_blockers.rs))

Then validate installed Spotify native/Flatpak with ordinary playback, already-paused state, ads/account variants, manual interaction, restart, and Connect; validate YouTube on Chromium-family and Firefox with one video, competing tabs, Picture-in-Picture, ads, live streams, navigation, and disabled integration. Include Spotify plus YouTube simultaneously and duplicate browser bridges. Measure pause latency, readiness delay, tail contamination, and exact restored target. These are future acceptance tests: **no playback commands, builds, or tests were run for this report**, and rolling upstream source is not proof of an installed release’s behavior.

## Conclusion

The main engineering challenge is maintaining truthful ownership across asynchronous recording and player lifecycles. A native MPRIS implementation can satisfy the common Spotify/YouTube workflow with little installation burden, provided its limits are visible. Treat richer browser control as evidence-driven follow-up; invest first in capture closure and race-safe restoration, because every eventual transport will depend on those foundations.
